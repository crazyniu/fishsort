# 05 开发规范

## 1. 代码（GDScript）

- **全量静态类型**：变量、参数、返回值都写类型。项目设置里把 `untyped_declaration`、`unsafe_*` 警告调成错误。
- 遵循 Godot 官方 GDScript 风格：文件与节点 `snake_case`，类名 `PascalCase`，常量 `UPPER_SNAKE`，信号用过去式（`fish_rescued`），私有成员加 `_` 前缀。`gdformat` 负责格式，不手工争论。
- `src/core/` 内：只继承 `RefCounted`；禁止 `Node`、autoload、`FileAccess`、`Time`、全局随机函数。时间由 `tick` 动作传入，随机数由传入的 RNG 提供。
- 场景脚本只做表现与输入转发，不写规则判断。单个脚本不超过 300 行，超了就拆。
- 节点引用用 `@export` 或 `%唯一名称`，不用长路径字符串 `get_node("A/B/C")`。
- 组件之间向上发信号、向下调方法；不跨层级直接抓兄弟节点。
- `await` 之后如果要访问节点，先 `is_instance_valid` / `is_inside_tree`。
- 注释只写「为什么」，用中文。
- 不提前抽象：同样的代码出现第三次再提取。

## 2. 配置与文案

- 数值全部进 `config/`，代码通过 `ConfigService` 读取，不写魔法数字。
- 玩家可见文字全部走 `tr("KEY")`，key 形如 `UI_HOME_START`，翻译在 `i18n/*.csv`，`zh_CN` 与 `en` 同步维护。
- 带文字的美术图（如标题字）出中英两版，或改用字体渲染。

## 3. 测试：只测值得测的

原则：测试是为了防止规则算错和关卡不可解，不是为了数量或覆盖率。

**要写**

| 范围 | 内容 |
|---|---|
| `src/core/rules` | 每条规则、每种障碍、每个道具各有少量用例，重点是连锁结算与胜负边界 |
| `src/core/gen` | 同种子输出一致；抽样种子生成的关卡能过校验 |
| 存档迁移 | 每个迁移函数一个用例 |
| 回归 | 修规则类 bug 时补一个能复现它的用例 |

**不写**

- 界面、动画、场景、`services`、`platform` 的单元测试。这些靠在编辑器里实际跑和验收。
- 只是转发调用、读配置、取值赋值的代码的测试。
- 覆盖率指标、快照测试、端到端自动化、为了测试而加的抽象层与 mock。
- 同一逻辑的重复用例：一个行为一个用例，边界值各一个，够了。

整套单测本地运行应在 30 秒内跑完，超过就删慢的、合并重复的。

## 4. CI（GitHub Actions）：一条流水线，三分钟内

只在 **向 `main` 提 PR** 时触发，一个 job，顺序执行：

1. `gdlint` + `gdformat --check`
2. `godot --headless --import`（确认工程能加载、脚本无解析错误）
3. `./run.sh test`（仅 `src/core` 的 GUT 用例）
4. `./run.sh level-verify-changed`（只校验本次 PR 改动的关卡文件）

**CI 里不做**：

- 不在每次 push 都跑；不设定时任务。
- 不做多平台导出构建矩阵、不跑真机或模拟器、不跑界面自动化。
- 不卡覆盖率，不做全量关卡校验（上千局机器人模拟只在本地 `./run.sh level-verify` 或发版前手动跑）。
- 不新增 job。要加检查项，先证明它拦得住真实出现过的问题，并且总时长仍在三分钟内。

发版导出（三端构建）是手动触发的独立 workflow，不属于 CI。

## 5. 项目管理（GitHub）

仓库：`crazyniu/fishsort`。

- **Milestones**：对应 `docs/07` 的 M0–M6。
- **Issues**：一件可独立验收的事一个 issue，用仓库里的模板（功能 / 缺陷 / 美术需求）。美术需求 issue 就是给 Codex 的 brief 的索引。
- **Labels**：`core` `game` `ui` `platform` `level` `art` `docs` 表示范围；`bug` `feat` `chore` 表示类型；`wechat` `douyin` `android` 表示平台；`blocked` 表示等用户或等资质。
- **Project 看板**：Todo → Doing → 待验收 → Done。「待验收」是等用户看界面或美术的状态。
- **分支与 PR**：`main` 受保护、始终可运行；功能在 `feat/简述`、修复在 `fix/简述`；一个 PR 关联一个 issue（`Closes #n`），CI 通过后 squash 合并。
- **提交信息**：`类型(范围): 说明`，类型取 `feat / fix / refactor / docs / test / chore / art / level`，说明用中文。例：`feat(core): 锁链泡结算`。
- **Releases**：每次提审打 tag `v主.次.修`，Release 说明里写三端各自的构建号。
- 规则变更的文档与代码放同一个 PR。
- 不提交：`.godot/`、导出产物、`art/raw/`、任何密钥与签名文件。`*.import` 与 `*.uid` 文件要提交。

## 6. 性能预算（以三四年前的中低端安卓机为准）

| 指标 | 预算 |
|---|---|
| 帧率 | 局内稳定 60，最低不低于 45 |
| Draw Call | 局内 ≤ 40，其它界面 ≤ 60 |
| 冷启动到可点击 | 小游戏与 Android 的目标值在 M0 验证后定 |
| 同屏鱼 | 160 条不掉帧 |

鱼、气泡、飞行特效走对象池；鱼共用图集以合批；局内 `_process` 里不做分配。

## 7. 广告与埋点

- 所有广告调用经 `AdService`，由它读 `ads.json` 做频控；业务代码不直接调平台。
- 激励视频只有返回 `DONE` 才发奖；`UNAVAILABLE` 时给出提示且不扣次数。
- 每个广告位、每关的开始 / 胜利 / 失败 / 复活 / 道具使用都要埋点，事件名集中定义在 `src/services/analytics_events.gd`。

## 8. 完成标准

1. 对应文档已更新。
2. CI 通过。
3. 在编辑器里实际跑过相关流程。
4. 涉及平台能力的，在对应平台开发者工具或真机验证过；没验证的在 PR 说明里明写「未在 X 平台验证」。
5. 没有新增魔法数字、硬编码文案、跨层调用。
